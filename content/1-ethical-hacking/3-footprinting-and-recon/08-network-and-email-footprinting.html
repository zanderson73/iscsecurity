1. Overview & Threat Landscape

Network and email footprinting are complementary disciplines. Network reconnaissance maps the logical topology; gateways, transit paths, asymmetric routes, and security appliances, while email footprinting maps the human and messaging perimeter: mail gateways, authentication posture, and the metadata leakage inherent in every sent message. Together they answer two critical questions: How does traffic enter the environment? and How do people communicate outside of it?

Modern adversaries do not treat traceroute as a mere "ping with hops." They use it to:

  • Identify asymmetric routing paths that bypass DDoS mitigations or geo-fencing.
  • Locate security appliances (WAFs, IDS/IPS, DLP proxies) by spotting anomalous latency spikes or ICMP-rate-limited hops.
  • Discover upstream ISP chokepoints or peering relationships for supply-chain or upstream-compromise scenarios.
  • Map internal RFC-1918 address space leaked via TTL-exceeded messages or traceroute responses from misconfigured edge devices.

Simultaneously, email footprinting provides:

  • MX and gateway enumeration that reveals whether a target uses cloud mail (Microsoft 365, Google Workspace) or legacy on-premise Exchange.
  • Security-appliance versioning extracted from X- headers and SMTP banners.
  • Geolocation of mail infrastructure and data-residency boundaries (EU, US, APAC).
  • Spear-phishing pretext material derived from internal hostnames, job titles, and routing paths in Received headers.
BlueOps Note:
Every hop in a traceroute and every Received header in an email is a piece of organisational intelligence that your perimeter defences are broadcasting to anyone who asks. The attacker's advantage is simply paying attention.

2. Adversarial Methodology: Phased Recon

  1. Phase 1: ASN & NetRange Baseline: Correlate DNS-resolved IPs with Regional Internet Registry (RIR) allocations. Extract CIDR, Origin AS, and upstream provider relationships.
  2. Phase 2: Multi-Protocol Topology Mapping: Execute Internet Control Message Protocol (ICMP), User Datagram Protocol (UDP), and Transmission Control Protocol (TCP) traceroutes from diverse vantage points residential Internet Service Provider (ISP), cloud Virtual Machine (VM), corporate Virtual Private Network (VPN). Compare outputs to isolate persistent hops from ephemeral ones.
  3. Phase 3: Path Analysis & Appliance Fingerprinting: Correlate latency spikes, missing hops (* * *), and MSS values to infer firewall placement, MPLS clouds, and NAT boundaries.
  4. Phase 4: Mail Infrastructure Enumeration: Query MX, SPF, DKIM, DMARC (TXT), and SMTP banners. Identify the exact mail-security stack (Proofpoint, Mimecast, Barracuda, Microsoft EOP).
  5. Phase 5: Header Harvesting & Parsing: Collect legitimate emails (newsletters, support auto-replies, job alerts, marketing) and extract full raw headers. Parse Received chains, Authentication-Results, and X-Mailer fields.
  6. Phase 6: Identity Correlation (OSINT Pivot): Use harvested email addresses and header-derived IPs to query breach databases, social platforms (Holehe, Social Catfish), and geolocation services.
  7. Phase 7: Weaponisation Prep: Synthesise findings into phishing pretexts that mirror internal routing, spoof trusted gateway domains, or exploit known mail-gateway parsing quirks.

5. Traceroute Techniques & Topology Mapping

Traceroute is an active measurement tool that exploits the TTL field in IP headers. Modern defenders filter ICMP, so Red Teams must be fluent in ICMP, UDP, and TCP variants and be able to correlate them to reveal the true path.

5.1 ICMP Traceroute (Windows — tracert)

Windows ships with tracert, which by default sends ICMP Echo Request probes.

C:\> tracert -d iscsecurity.org

Tracing route to iscsecurity.org [10.0.2.15]
over a maximum of 30 hops:

  1    <1 ms    <1 ms    <1 ms  10.0.2.2
  2    <1 ms    <1 ms    <1 ms  10.0.10.1
  3     1 ms     1 ms     1 ms  10.0.2.15

Trace complete.

Analysis: Three hops visible. Hop 1 is the local gateway (10.0.2.2). Hop 2 (10.0.10.1) is an intermediate edge router. Hop 3 is the target. All sub-millisecond latencies confirm a local-segment or virtual-lab path.

5.2 TCP Traceroute (Layer-4 Bypass)

When Internet Control Message Protocol (ICMP) is filtered by edge devices, TCP-based probes on ports 80 or 443 often succeed because firewalls must permit the established application traffic.

$ sudo tcptraceroute iscsecurity.org 443

Running:
 -T -O info -p 443 iscsecurity.org
traceroute to iscsecurity.org (10.0.2.15), 30 hops max, 60 byte packets
 1  10.0.2.2 (10.0.2.2)    0.523 ms  0.489 ms  0.512 ms
 2  10.0.10.1 (10.0.10.1)    0.891 ms  0.834 ms  0.812 ms
 3  iscsecurity.org (10.0.2.15)    1.102 ms  1.093 ms  1.087 ms

Analysis: The <syn,ack,mss=1460> at every hop indicates a stateful device responded with TCP SYN-ACK, implying these hops are either routed L3 hops with TCP-proxy behaviour or the path is flat and every hop resolves to the same endpoint due to load-balancing or ICMP rate-limiting. The consistent MSS of 1460 bytes suggests standard Ethernet MTU with no MPLS overhead.

5.3 UDP Traceroute (Linux Classic)

Traditional Linux traceroute sends UDP to high ports (33434+), relying on ICMP Port Unreachable or TTL Exceeded.

$ sudo traceroute -n -q 1 -N 32 iscsecurity.org

traceroute to iscsecurity.org (10.0.2.15), 30 hops max, 60 byte packets
 1  10.0.2.2  0.451 ms
 2  10.0.10.1  0.782 ms
 3  10.0.2.15  1.045 ms

5.4 Traceroute with AI-Assisted Command Generation

AI assistants can draft recon commands, but they must be sanity-checked before execution.

$ sudo sgpt --shell "Generate a traceroute command to map hops to iscsecurity.org using TCP port 443 and save the output to trace.txt"

OPSEC Warning:
AI-generated commands may include aggressive flags (-I for ICMP, high packet rates) or unintended destination formats. Always validate against your RoE. Never run active discovery against targets outside scope.

5.5 Multi-Vantage Point Correlation

Run identical traces from a residential ISP, a cloud VM (e.g., AWS), and a corporate VPN exit node. Asymmetric routing often means the forward and reverse paths differ. Persistent hops across all three vantage points indicate shared core infrastructure (likely impossible to alter); hops unique to one vantage point reveal edge-specific dependencies. 

Vantage Point: Residential ISP (London)
  Hop 5:  4.68.1.1   (Level3/AS3356)  12.4 ms
  Hop 6:  10.0.10.1  (Target edge)      14.1 ms

Vantage Point: AWS (us-east-1)
  Hop 4:  54.239.1.1 (AWS backbone)     2.1 ms
  Hop 5:  10.0.10.1  (Target edge)      3.4 ms

Vantage Point: Corporate VPN (Singapore)
  Hop 8:  203.78.1.1 (Local ISP)        89.2 ms
  Hop 9:  10.0.10.1  (Target edge)      91.5 ms

Conclusion: 10.0.10.1 is a persistent shared edge. Latency from Singapore suggests trans-Pacific routing.

7. Email Footprinting & Header Intelligence

Email headers are a timestamped, hop-by-hop journal of a message's life. They expose not only the infrastructure but also the habits and security hygiene of the target organisation.

7.1 What Email Tracking Can Reveal

  • Originating / transit IP addresses: Geolocation and ASN pivot points.
  • Mail servers & security gateways: Vendor and version hints from Received and X- headers.
  • Time stamps: Time-zone offsets and processing latency at each hop (useful for estimating internal queue loads).
  • Client software: X-Mailer, User-Agent, or X-Microsoft-Antispam reveal standard endpoints.
  • Forwarding & proxying: Multiple Received fields or X-Forwarded-For expose mail-flow architecture.
  • Authentication posture: Authentication-Results shows SPF, DKIM, and DMARC disposition (pass/fail/none).

9. Case Studies

Case Study 1: The Silent Librarian (Mabna Institute) — Email Infrastructure Recon for Spear-Phishing

The Iranian Mabna Institute targeted universities and research institutions globally. Prior to sending credential-harvesting emails, they performed systematic MX and DNS enumeration to determine whether targets used cloud-hosted email (easy DMARC/SPF) or legacy on-premise Exchange. For on-premise targets, they harvested X-Mailer and Received headers from public mailing-list archives to identify internal hostnames (e.g., exch2013.university.local) and NTLM authentication prompts. This allowed them to craft fake library-login pages that mirrored the exact internal naming convention, dramatically increasing click-through rates. The initial entry was not malware, it was email-header OSINT turned into pretext.

Internal hostnames exposed in email headers are not "metadata"; they are attack surface. Strip or rewrite internal Received fields at the external gateway.

Case Study 2: Accellion/FTA Supply Chain — Traceroute Topology Mapping to Identify Shared Edge Infrastructure

During reconnaissance against organisations using the Accellion file-transfer appliance, Red Teams (and later threat actors) used multi-protocol traceroute from global vantage points to map the network paths to Accellion-managed hosts. They identified that dozens of victim organisations shared the same upstream ISP edge router and DDoS-scrubbing service. While the ultimate exploit targeted the Accellion appliance itself, the traceroute phase proved that compromising the shared edge infrastructure (or simply understanding its latency profiles) could help adversaries distinguish between production and disaster-recovery instances based on hop count alone. In one engagement, a 2-hop difference between primary and DR sites revealed the failover architecture, allowing the Red Team to recommend out-of-band path diversity.

Traceroute topology is infrastructure intelligence. Segment failover paths across different ASNs and obscure internal hop responses to prevent topology deduction.

10. OPSEC & Legal Boundaries

10.1 Operational Security

  • Active Probe Attribution: Traceroute generates TTL-expired packets and TCP SYNs that are logged by border firewalls and ISP DDoS mitigation systems. Rotate source IPs and avoid repeated scans from the same cloud instance.
  • AI Command Sanity: AI-generated traceroute commands may include -I (raw ICMP sockets requiring root), high-frequency probes, or broadcast-target mistakes. Verify flags match your OS and RoE.
  • Email Harvesting Hygiene: Subscribing to newsletters solely to harvest headers may violate terms of service and anti-spam laws. Use publicly archived mailing-list posts where possible.
  • Holehe Rate Limits: Bulk queries against Holehe may trigger rate-limiting or platform-side account-lockout protections. Space out queries and avoid testing client VIP emails against live platforms without consent.
  • SMTP Banner Probing: Direct MX connection on port 25 is often logged and may trigger tarpits or greylisting. Use minimally one banner grab per MX, not repeated connects.

10.2 Legal Boundaries

Framework Constraint Risk
ECPA (USA) / CMA (UK) Harvesting, storing, or analysing email headers containing PII may implicate electronic communications privacy laws if obtained without consent or outside authorised scope. Criminal penalties; civil liability; loss of PI insurance.
GDPR (EU) Email addresses, geolocation derived from IPs, and header-derived behavioural data are personal data. Processing must have a lawful basis. Fines up to 4% global turnover; DPA investigation.
Platform ToS (LinkedIn, GitHub, etc.) Holehe and Social Catfish-style correlation may violate scraping or account-enumeration prohibitions. IP ban; account termination; CFAA exposure.
RoE / Engagement Contract Active traceroute through client ISP partners or email subscription from impersonation accounts may exceed scope. Contract breach; reputational damage; legal action.
Golden Rule (ROE):
If you are not certain the activity is within signed Rules of Engagement (RoE) and legal review, do not execute it. When in doubt, use only passive, unauthenticated techniques.

11. Quick Triaging Checklist: Network & Email Recon Workflow

□ Scope Confirmation
    □ Active traceroute authorised (ICMP/UDP/TCP)?
    □ Email header collection limited to public archives / authorised recipients?
    □ SMTP banner grabbing approved?

□ Phase 1 — ASN & NetRange Baseline
    □ Resolve target domains to IPs (A/AAAA).
    □ Query RIR (ARIN/RIPE/APNIC/LACNIC/AFRINIC) for NetRange, CIDR, Origin AS.
    □ Query RADB / BGP.HE.net for upstream peers and route objects.

□ Phase 2 — Multi-Protocol Topology Mapping
    □ Run ICMP traceroute (Windows tracert or Linux -I).
    □ Run TCP traceroute (tcptraceroute or traceroute -T -p 443).
    □ Run UDP traceroute (Linux traceroute default).
    □ Run same set from ≥2 vantage points (residential + cloud + VPN).

□ Phase 3 — Path Analysis
    □ Identify persistent hops vs. ephemeral hops.
    □ Map latency spikes to potential security appliances.
    □ Document asymmetric routes (forward vs. return path divergence).
    □ Flag any RFC-1918 IPs appearing in public traceroutes.

□ Phase 4 — Mail Infrastructure Enumeration
    □ Query MX, SPF, DKIM, DMARC (TXT) records via dig.
    □ Perform SMTP banner grab on each MX host (port 25 / 587).
    □ Note gateway vendor (Proofpoint, Mimecast, Barracuda, Microsoft EOP).

□ Phase 5 — Header Harvesting & Parsing
    □ Collect raw headers from auto-responders, newsletters, or mailing lists.
    □ Parse Received chain (oldest = bottom, newest = top).
    □ Extract Authentication-Results (SPF/DKIM/DMARC disposition).
    □ Identify internal hostnames / IPs leaked in intermediate hops.

□ Phase 6 — OSINT Correlation
    □ Geolocate header IPs via ipinfo.io / IP2Location.
    □ Run Holehe against discovered addresses for platform registration.
    □ Cross-reference with Social Catfish / breach databases where authorised.

□ Phase 7 — Weaponisation Prep (if authorised)
    □ Map gateway vendor to known bypass techniques or template formats.
    □ Use internal hostnames from headers to craft realistic pretexts.
    □ Time phishing sends to align with time-zone and business-hour patterns.

□ Phase 8 — Reporting & Sanitisation
    □ Save raw traceroute outputs with UTC timestamp and source IP.
    □ Save raw .eml / header text files; do not rely solely on parsed views.
    □ Redact personal email addresses and internal IPs in public-facing annexes.
    □ Append defensive mitigations to every finding (header rewrite, DMARC, etc.).

13. Defensive Countermeasures & Threat Mapping

13.1 Blue Team Mitigations

  • Suppress Internal IPs in TTL-Exceeded Responses: Configure edge routers to drop or rewrite ICMP TTL-exceeded messages so they do not contain internal RFC-1918 source addresses.
  • Filter Traceroute Probes: Rate-limit ICMP and UDP high-port probes at the border. Consider blocking inbound UDP traceroute entirely unless required for operations.
  • Rewrite Email Headers at Gateway: Strip or mask internal Received hops, X-Mailer, and server hostnames before messages exit the organisation. Replace with generic gateway identifiers.
  • Remove SMTP Version Banners: Disable vendor-specific SMTP greeting strings (e.g., Microsoft ESMTP MAIL Service) to prevent version-based targeting.
  • Enforce Strict DMARC: Publish DMARC p=reject with RUA reporting to prevent domain spoofing and to receive telemetry on abuse attempts.
  • Header Sanitisation Rules: Remove X-MS-Exchange-Organization-AuthAs, X-Proofpoint-*, and other vendor-specific headers that reveal security-stack details.
  • Monitor for OSINT Correlation: Alert when corporate emails are queried in bulk against public verification APIs (difficult but feasible via threat-intel feeds).
  • Segment Failover Paths: Ensure primary and disaster-recovery network paths traverse different ASNs or at least different edge routers to prevent single-hop topology mapping.

Network paths and email headers are two sides of the same coin, both expose the seams between internal trust and external exposure. A traceroute hop leaking a 10.x.x.x address is no less critical than an email header leaking EXCH-01.corp.local.

14. Ethical Considerations & Engagement Scope

  • Active vs. Passive Boundaries: Traceroute is active and generates probe traffic, obtain explicit authorisation. Email header analysis from public archives is passive; subscribing to lists solely for recon may not be.
  • PII Minimisation: Email headers contain names, roles, device hostnames, and approximate locations. Retain only what is necessary to demonstrate risk. Securely purge the rest.
  • Platform Terms: Holehe and Social Catfish queries against third-party platforms must not violate scraping or account-enumeration policies. Do not brute-force corporate directories via sign-up pages.
  • No Interference: Never alter TTL values to inject packets into internal routing tables, and never send spoofed emails "to test" without a dedicated social-engineering workstream in the RoE.
  • Responsible Disclosure: When internal hostnames or IP ranges are discovered exposed in headers/traceroutes, report them as configuration vulnerabilities, not mere "observations."

Scenario-Based Question

Scenario: You are conducting a Red Team engagement against Fabricated Industries, a mid-sized technology and manufacturing conglomerate. Your Rules of Engagement permit active network reconnaissance (traceroute, ping sweeps) and passive email header analysis from publicly available sources. Initial open-source research has identified the primary domain fabricatedtech.com and several public IP addresses hosting the company's web presence.

Task: Design a comprehensive network and email reconnaissance workflow to map the organisation's network topology, identify security appliances, enumerate mail infrastructure, and extract intelligence from email headers to support social engineering pretext development.

Suggested Approach:
  • Phase 1: ASN & NetRange Baseline: Resolve target domains to IP addresses. Query RIR databases (ARIN, RIPE, APNIC) for NetRange, CIDR, and Origin AS. Identify upstream providers and cloud hosting regions.
  • Phase 2: Multi-Protocol Topology Mapping: Execute ICMP traceroute (tracert / traceroute -I), TCP traceroute (tcptraceroute on port 443), and UDP traceroute from multiple vantage points (residential ISP, cloud VM, corporate VPN). Compare outputs to identify persistent vs. ephemeral hops.
  • Phase 3: Path Analysis & Appliance Fingerprinting — Correlate latency spikes, missing hops (* * *), and MSS values to infer firewall placement, MPLS clouds, and NAT boundaries. Document any RFC-1918 IP addresses appearing in public traceroutes.
  • Phase 4: Mail Infrastructure Enumeration: Query MX, SPF, DKIM, and DMARC records via dig. Perform SMTP banner grabbing on each MX host (nc -vz mail.target.com 25). Identify mail gateway vendors (Proofpoint, Mimecast, Barracuda, Microsoft EOP).
  • Phase 5: Header Harvesting & Parsing: Collect raw email headers from public sources (mailing lists, auto-responders, newsletters). Parse Received chains (oldest = bottom, newest = top). Extract internal hostnames, IP addresses, and authentication results. Identify X-Mailer and vendor-specific headers.
  • Phase 6: OSINT Correlation: Geolocate header-derived IPs via ipinfo.io / IP2Location. Run Holehe against discovered email addresses to identify platform registrations (LinkedIn, GitHub, Twitter). Cross-reference with breach databases (HIBP, DeHashed) for credential exposure.
  • Phase 7: Weaponisation & Blue Team Handoff: Map gateway vendor to known bypass techniques. Use internal hostnames from headers to craft realistic pretexts. Time phishing sends to align with time-zone and business-hour patterns. Provide defensive mitigations: header sanitisation, DMARC p=reject, and suppression of internal IPs in TTL-exceeded responses.
