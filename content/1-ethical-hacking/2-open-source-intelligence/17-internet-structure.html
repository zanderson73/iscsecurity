1. Macro-Layer Cartography: Mapping the Target's Presence on the Internet Graph

Adversary Goals: Before querying infrastructure, define the target's position within the global routing table, DNS hierarchy, and peering ecosystem. This reveals not just what they own, but where they physically and logically connect to the internet.

The Internet is a global "network of networks" built on the TCP/IP stack. Underneath it sit ISPs, long-haul backbones, and Internet Exchange Points (IXPs), while above it sit DNS, CDNs, clouds (AWS/Azure/GCP), and edge nodes. All relevant to recon and attack-surface mapping.

IPv6 adoption and Zero Trust architectures continue to change how assets are discovered and enumerated, increasing the importance of multi-source reconnaissance and cloud-aware tooling.

1.1 The Structural Dossier

Build a target file containing:

  • Autonomous System Numbers (ASNs): Their own and acquired subsidiaries.
  • Registered CIDRs: inetnum / inet6num objects across all RIRs.
  • Upstream & Peer ASNs: Transit providers (Tier 1/2) and settlement-free peers.
  • IXP Presence: Internet Exchange Points where they maintain peering fabric.
  • DNS Authority Chain: Root nameserver → TLD NS → Authoritative NS → Zone apex.
  • Certificate Transparency Baseline: All historical TLS certificates issued to their domains.
  • RIR Handles: Administrative, technical, and abuse contacts linked to their resources.

1.2 Pivot Points

Internet structure reconnaissance pivots on:

  • ASN → Prefixes → Peers → IXPs → Physical Facilities
  • Domain → Authoritative NS → NS Version / Geographic Distribution → Zone Transfer Misconfigurations
  • Certificate CN/SAN → Origin IP (CDN bypass) → Unprotected Web Infrastructure
  • IP Geolocation Clustering → Data Center Mapping → Physical Perimeter Correlation
Red Team Note:
Internet-structure reconnaissance is almost entirely passive and generates zero packets to the target's edge. It is the highest-return, lowest-risk phase of external reconnaissance.

3. Master Advanced Query Syntax

Adversary Goals: RIR RPSL, RDAP, BGP, and DNS Authority commands for precision internet-structure reconnaissance.

3.1 Routing Registry & ASN Enumeration

# Query ARIN RDAP for ASN registration (JSON output for parsing)
curl -s https://rdap.arin.net/registry/autnum/15169 | \
  jq '.name, .handle, .startAutnum, .endAutnum, .entities[0].vcardArray[1][] | select(.[0]=="email") | .[3]'

# Query RIPE NCC for all route objects originating from target ASN
whois -h whois.ripe.net -i origin AS12345

# Query RADb for all prefixes announced by ASN (legacy but widely used)
whois -h whois.radb.net "!gAS12345"

# Bulk IP-to-ASN mapping via Team Cymru (netcat mode for scale)
{ echo "begin"; echo "verbose"; cat target_ips.txt; echo "end"; } | nc whois.cymru.com 43

# Single IP verbose lookup
whois -h whois.cymru.com " -v 203.0.113.45"

3.2 PeeringDB & IXP Intelligence

# Retrieve network record by ASN (includes policy, website, prefix counts)
curl -s "https://api.peeringdb.com/api/net?asn=15169" | \
  jq '.data[] | {name, info_prefixes4, info_prefixes6, policy_general, website}'

# Extract all IXPs where target maintains presence and associated peering IPs
# First get the internal net_id
NET_ID=$(curl -s "https://api.peeringdb.com/api/net?asn=15169" | jq '.data[0].id')

# Then pull IX LAN entries (reveals private peering IP space on IX fabrics)
curl -s "https://api.peeringdb.com/api/netixlan?net_id=${NET_ID}" | \
  jq '.data[] | {ix_name: .name, ipaddr4, ipaddr6, speed, status}'

3.3 DNS Authority & Structural Mapping

# Full DNS delegation trace (touches root, TLD, and target authoritative NS)
dig +trace +nodnssec target.com

# Identify authoritative nameservers only
dig +short NS target.com

# Attempt zone transfer against each authoritative NS (structural goldmine)
for ns in $(dig +short NS target.com); do
    echo "[*] Trying AXFR against $ns..."
    dig @$ns target.com AXFR
done

# Nmap DNS zone transfer script (alternative)
nmap --script dns-zone-transfer --script-args dns-zone-transfer.domain=target.com

# DNSSEC validation chain extraction (identify absence = cache poisoning opportunity)
dig +dnssec +multi DNSKEY target.com
dig +dnssec +multi DS target.com

# Extract MX records (often bypass WAF/CDN and point to unprotected mail gateways)
dig +short MX target.com
host -t MX target.com

3.4 Certificate Transparency & Origin IP Discovery

# Pull all certificate entries for domain and subdomains from crt.sh
curl -s "https://crt.sh/?q=%.target.com&output=json" | \
  jq -r '.[].name_value' | sort -u > ct_domains.txt

# Resolve candidate origin subdomains (often non-proxied by CDN)
grep -iE "^(origin|direct|cdn[0-9]|ftp|mail|webmail|cpanel|web[0-9]|dev|stage)" ct_domains.txt | \
  while read domain; do
    host "$domain"
  done | grep "has address" | awk '{print $4}' | sort -u > potential_origins.txt

# Verify if origin IP responds with target content using correct Host header
for ip in $(cat potential_origins.txt); do
  STATUS=$(curl -s -o /dev/null -w "%{http_code}" --connect-timeout 3 -H "Host: target.com" "http://$ip/")
  if [ "$STATUS" == "200" ] || [ "$STATUS" == "301" ] || [ "$STATUS" == "302" ]; then
    echo "[+] ORIGIN CANDIDATE: $ip (HTTP $STATUS)"
  fi
done

3.5 Macro-Geolocation Clustering

# Resolve primary domain
get_domain_ip --domain target.com

# Geolocate resolved IP

# For larger netblocks, cluster IPs by country/region to find facility concentrations
# (Assuming you have a list of live hosts from prior reconnaissance)

5. Automate Ingestion via API Pipelines

Adversary Goals: From global routing tables to operational target maps. Manual WHOIS and DNS queries do not scale across multi-continental organizations. Internet-structure data must be normalized into a relational or graph database for pivot analysis.

5.1 RIPE Stat + PeeringDB Ingestion Pipeline

#!/usr/bin/env python3
# Conceptual adversary tool: Internet structure ingestion pipeline
import requests
import sqlite3

DB = "internet_structure.db"
conn = sqlite3.connect(DB)
c = conn.cursor()

# Schema: Macro-level internet presence
c.execute('''CREATE TABLE IF NOT EXISTS asn_prefixes (
                id INTEGER PRIMARY KEY, asn TEXT, prefix TEXT, rir TEXT,
                source TEXT, first_seen TEXT, rpki_status TEXT)''')

c.execute('''CREATE TABLE IF NOT EXISTS peering (
                id INTEGER PRIMARY KEY, asn TEXT, ix_name TEXT,
                peering_ip TEXT, speed_mbps INTEGER, facility_city TEXT)''')

def ingest_ripe_announced(asn):
    url = f"https://stat.ripe.net/data/announced-prefixes/data.json?resource=AS{asn}&starttime=2024-01-01T00:00:00"
    r = requests.get(url, timeout=20).json()
    for prefix_data in r.get("data", {}).get("prefixes", []):
        prefix = prefix_data.get("prefix")
        c.execute("INSERT INTO asn_prefixes (asn, prefix, source, first_seen) VALUES (?,?,?,?)",
                  (asn, prefix, "ripe-stat", prefix_data.get("timelines", [{}])[0].get("starttime")))
    conn.commit()

def ingest_peeringdb(asn):
    net_url = f"https://api.peeringdb.com/api/net?asn={asn}"
    net_resp = requests.get(net_url, timeout=20).json()
    if not net_resp.get("data"):
        return
    net_id = net_resp["data"][0]["id"]
    net_name = net_resp["data"][0]["name"]

    ixlan_url = f"https://api.peeringdb.com/api/netixlan?net_id={net_id}"
    ixlan_resp = requests.get(ixlan_url, timeout=20).json()
    for entry in ixlan_resp.get("data", []):
        c.execute("INSERT INTO peering (asn, ix_name, peering_ip, speed_mbps) VALUES (?,?,?,?)",
                  (asn, entry.get("name"), entry.get("ipaddr4"), entry.get("speed", 0)))
    conn.commit()

TARGET_ASNS = ["12345", "67890"]
for asn in TARGET_ASNS:
    ingest_ripe_announced(asn)
    ingest_peeringdb(asn)

conn.close()

5.2 Automated Origin-IP Hunter (CDN Bypass)

#!/usr/bin/env python3
# Conceptual adversary tool: Origin IP discovery via certificate transparency
import subprocess
import requests
import json

def hunt_origins(domain):
    # Phase 1: crt.sh extraction
    url = f"https://crt.sh/?q=%.{domain}&output=json"
    r = requests.get(url, timeout=30).json()
    subdomains = list({entry["name_value"] for entry in r})

    # Phase 2: Filter high-fidelity origin candidates
    keywords = ["origin", "direct", "cdn", "mail", "ftp", "webmail", "cpanel", "web", "dev", "stage", "app", "api"]
    candidates = [s for s in subdomains if any(k in s for k in keywords)]

    origins = []
    for cand in candidates:
        # Resolve via system host command
        try:
            ip = subprocess.check_output(["dig", "+short", cand], text=True).strip().split("\n")[0]
            if ip:
                origins.append({"subdomain": cand, "ip": ip})
        except Exception:
            continue

    # Phase 3: Verify with Host header injection (OPSEC: route through proxy/VPS)
    verified = []
    for item in origins:
        try:
            resp = requests.get(f"http://{item['ip']}/", headers={"Host": domain}, timeout=5, allow_redirects=False)
            if resp.status_code in [200, 301, 302, 401, 403] and domain.lower() in resp.text.lower():
                item["status"] = resp.status_code
                item["verified"] = True
                verified.append(item)
        except Exception:
            continue

    with open(f"{domain}_origins.json", "w") as f:
        json.dump(verified, f, indent=2)

hunt_origins("target.com")

5.3 RIR RDAP Bulk Normalization

#!/bin/bash
# Bulk query ARIN RDAP for Org handles and associated CIDRs
for asn in $(cat target_asns.txt); do
  echo "[*] Querying RDAP for AS${asn}"
  curl -s "https://rdap.arin.net/registry/autnum/${asn}" | \
    jq -r '.entities[]? | select(.roles[]? == "registrant") | .handle' >> arin_handles.txt
done

# For each Org handle, pull associated networks
for handle in $(cat arin_handles.txt | sort -u); do
  curl -s "https://rdap.arin.net/registry/entity/${handle}" | \
    jq -r '.networks[]?.cidr0_cidrs // empty | .[] | .v4prefix // .v6prefix' >> target_cidrs.txt
done

6. Breach Landscape: Operational Reality in Mid‑2026

Adversary Goals: Understand the active breach landscape to prioritize intelligence gathering, map compromised supply chains, and mitigate credential and session-token exposure.

  • SaaS and Cloud Campaign Dominance: Coordinated extortion clusters continue to prioritize corporate software platforms and identity providers, proving that attackers are logging in with stolen access, often session cookies and tokens rather than breaking traditional perimeters. Expect stealer logs and infostealer telemetry to remain the primary source of initial access broker inventory.

  • Have I Been Pwned (HIBP) and Stealer‑Log Ingestion: Continuous high‑volume indexing of stealer logs and aggregated dumps persists through 2026, reinforcing the need for real‑time identity‑exposure monitoring. Raw password counts alone are becoming less meaningful as passkey adoption grows; monitor for session token, corporate SSO cookie, and API‑key exposure alongside traditional credentials.

  • Vendor Blast Radius Amplification: Breaches targeting central third‑party platforms (healthcare, fintech, education, and critical SaaS intermediaries) continue to cause cascading exposure down the supply chain. Verify assets continuously rather than assuming trusted‑vendor status.

  • AI‑Augmented Parsing and Targeting: Adversaries are increasingly using automated tooling to parse multi‑gigabyte stealer dumps at scale, prioritizing high‑value corporate VPN and VDI endpoints. Defenders should assume that any credential appearing in a stealer log will be tested against corporate edge services within hours, not weeks.

7. TOR & Anonymity: Platform Notes

The Tor Project’s migration from legacy C components to the Rust‑based Arti stack remains an ongoing priority through 2026. Stable releases of Tor Browser continue to ship with anti‑fingerprinting improvements, channel‑security updates, and incremental deprecation of older protocol features. Mobile privacy offerings (including Arti‑based VPN/split‑tunnel tooling on Android) have moved beyond early beta for many users, though feature parity and platform support continue to evolve.

For operators, this means Tor should be used deliberately and with clear operational boundaries. During C2 or anonymity simulations, route Tor traffic through controlled infrastructure, document session identifiers, and avoid mixing operational traffic with personal browsing or unrelated recon. Expect additional circuit‑behaviour updates and feature deprecations as the transition to Arti progresses.

8. Verify and Triage Safely (OPSEC)

Adversary Goals: Internet-structure reconnaissance is predominantly passive, but poor OPSEC here exposes the operation during the earliest phase.

8.1 RIR & WHOIS OPSEC

  • RIR WHOIS daemons (port 43) log source IPs and are subject to rate-limiting. Favor RDAP (HTTPS REST APIs); they are less likely to trigger abuse alerts and are easier to proxy.
  • Bulk queries: Spread WHOIS requests across time or use multiple egress IPs. Team Cymru allows bulk submissions via TCP/43, but still tag your source.
  • IRR queries (RADb): Generally unrestricted, but repeated !iAS-SET expansions can be logged.
# Use RDAP over legacy WHOIS for attribution hygiene
curl -s --proxy socks5h://127.0.0.1:9050 https://rdap.arin.net/registry/autnum/15169 | jq '.'

8.2 DNS Authority Chain OPSEC

  • dig +trace queries the target's authoritative nameservers directly during the final iteration. Your source IP appears in their DNS query logs.
  • Mitigation: Use public resolvers (Google, Cloudflare) for non-recursive queries, but note that +trace inherently bypasses them. If strict passive reconnaissance is required, rely on archived DNS data (e.g., SecurityTrails, VirusTotal) rather than live traces.
# Use public resolver to avoid direct NS contact where possible
dig @8.8.8.8 +short NS target.com

# If trace is mandatory, route through engagement VPS
proxychains4 dig +trace target.com

8.3 PeeringDB & Platform Attribution

  • PeeringDB requires user accounts for API access beyond basic queries. Create engagement-specific burner accounts with no link to your organization or real identity.
  • API keys should be rotated post-engagement.

8.4 Origin IP Verification (Active)

Probing candidate origin IPs with spoofed Host headers is active contact with target infrastructure. This may:

  • Trigger WAF origin-protection alerts.
  • Log your IP on the target's origin server.
  • Expose your operation if the origin is instrumented.

Mitigation: Route all verification traffic through disposable VPS nodes or proxy pools.

# OPSEC-hardened origin probe
curl -s --connect-timeout 4 \
  --proxy http://disposable-vps-ip:3128 \
  -H "Host: target.com" \
  -H "User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)" \
  http://CANDIDATE_IP/

8.5 Cross-Check for Data Staleness

Routing registry data (IRR) is often stale compared to live BGP. An AS may no longer announce a prefix listed in RADb.

Validation: Cross-reference RIR-registered prefixes against live BGP tables via RIPE Stat or a looking glass before reporting them as current assets.

# Verify a prefix is currently announced in the global routing table
curl -s "https://stat.ripe.net/data/routing-status/data.json?resource=203.0.113.0/24" | \
  jq '.data.announced'

8.6 OPSEC Checklist for Internet-Structure Operations

  • ✅ All RIR RDAP queries routed through engagement proxies or Tor (--proxy socks5h://)
  • ✅ Legacy WHOIS port-43 queries minimized in favor of HTTPS RDAP

  • ✅ PeeringDB API authenticated with burner account (no personal/organizational linkage)

9. Practical Changes to Your Recon & Hygiene Workflows (Actionable)

  • Automate breach and session-token monitoring:
    Integrate API‑based breach monitoring (HIBP, DeHashed, IntelligenceX) and stealer‑log telemetry into CI/CD, identity hygiene, and SOC hand‑off workflows. In mid‑2026, exposure is increasingly about session cookies, SSO tokens, and API keys rather than static passwords alone. Automation should flag credential and session artefacts the moment they appear in fresh infostealer dumps or dark‑web markets.

  • Triangulate breach leads before acting:
    When an identity or credential surfaces in a dump, treat it as a lead, not a confirmed incident. Cross‑verify using HIBP, vendor advisories, CTI feeds, and automated dark‑web enumeration. This helps distinguish:
    • Mass credential‑stuffing lists and recycled old breaches
    • AI‑generated synthetic dumps (fabricated lists used for SEO, reputation attacks, or scam leverage)
    • Legitimate, high‑risk compromise with fresh session tokens or MFA bypass data
    Proper correlation prevents false escalations and focuses incident response where active exploitation is likely.

  • Instrument anonymous recon infrastructure with OPSEC rigour:
    When using Tor, VPN splits, or anti‑detect browsers for anonymous recon or C2 simulation, route traffic through dedicated, controlled infrastructure. Log connection times, circuit IDs, operator keys, and campaign identifiers so your traffic is clearly distinguishable from real‑world malicious actors. With the Tor Project’s ongoing Arti migration and mobile split‑tunnel betas maturing in 2026, expect platform changes that affect fingerprinting and exit‑node behaviour — review tooling quarterly rather than relying on static playbooks.

  • Prioritise healthcare, SaaS supply chains, and AI/ML infrastructure:
    Persistent targeting of healthcare, health‑tech SaaS platforms, and EMR ecosystems continues through 2026, often cascading through third‑party MSPs and identity brokers. Additionally, AI/ML supply chains (training‑data repositories, model‑serving endpoints, and vector‑DB exposure) have become high‑value recon targets. Treat any findings involving patient data, critical SaaS intermediaries, or AI pipeline assets as high severity, and escalate with breach‑ notification timelines in mind.

Passkey adoption is rising, but the transitional landscape means most enterprises still manage large legacy password estates alongside FIDO2/WebAuthn rollouts. Hygiene workflows must cover both paradigms until passwordless coverage is universal.

11. Defensive Countermeasures & Threat Mapping

Translating adversarial internet-structure reconnaissance into defense requires routing hygiene, DNS hardening, and continuous external monitoring.

Defensive Best Practices

  • RPKI/ROA Validation: Deploy RPKI ROAs for all announced prefixes to prevent route hijacking.
  • IRR Hygiene: Keep RADb/RIPE route objects current; remove stale prefixes immediately.
  • DNSSEC: Implement DNSSEC on all zones to prevent cache poisoning and integrity attacks.
  • Zone Transfer Restriction: Explicitly deny AXFR except from known secondary nameserver IPs.
  • Origin Protection: Ensure origin servers do not accept direct HTTP requests without proper Host headers; use ACLs.
  • Certificate Transparency Monitoring: Subscribe to CT log monitors (e.g., CertStream) for unauthorized certs.
  • External Attack Surface Management: Weekly automated checks against PeeringDB, RIPE Stat, and Shodan/Censys for your netblocks.
